# Troubleshooting

When something misbehaves. See also the [Setup guide](../Setup/Setup.md).

1. `sudo systemctl status restreamd` — is the controller even running? It validates `config.json` on startup and refuses to run on a broken one, naming the field it choked on, so a unit that won't come up is almost always a config problem rather than a stream problem.
2. `journalctl -u restreamd -f`, or `logs/controller.log` — the controller's own log; both carry the same lines.
3. Per-process logs, one set per **platform** (not per source): `logs/ffmpeg-relay-<platform>.log` (reading the source), `logs/ffmpeg-backup-<platform>.log` (fallback preset playback), `logs/ffmpeg-out-<platform>.log` (the push to the platform) — check these if the problem looks like a video/audio issue on one specific platform rather than a switching-logic issue. Two kinds of platform have no `out-` ffmpeg log, because their push goes through the controller's own RTMP client instead of ffmpeg: an RTMP+VOD one (Twitch VOD Track) and the Enhanced Broadcasting arm. Their errors land in the controller log.
4. A platform shows **behind (N drops)** on the Control tab — that platform's upload can't keep up with the source bitrate; it drops frames and resyncs on the next keyframe. Check its ping and the VPS's upstream bandwidth to that platform.
5. If the backup video looks "wrong" (not the file/preset you expected) — prepared backup segments live in `tmp/backup-cache/`, content-addressed by source identity **and** target parameters (resolution/fps/bitrate/channels, or the whole ladder for an Enhanced Broadcasting platform) and shared across every platform that needs the same ones; a `<hash>.json` sidecar records exactly what each artifact was built from. Delete the directory's contents to have the service rebuild them on the next stream start.
    - Preparing those segments is the only work here that transcodes, so it is the only work that can eat a whole core. On a 1-CPU VPS it is deliberately kept out of the broadcast's way: at most `max_concurrent_transcodes` ffmpeg at a time (default 1, even when several platforms need different parameters), `transcode_threads` threads each (default 1 — inside a container ffmpeg would otherwise read the *host's* core count and spawn far more threads than the quota allows), and at the lowest CPU priority. Both are `config.json` fields; raise them if the VPS actually has spare cores. The controller also warms the cache at startup, while the machine is idle, using the parameters each platform ended up with last time, and stops that the moment a source starts publishing — so a stream start usually finds the artifacts already there.
    - How far that preparation has got is the **fallback-preparer** row in the Status tab's Components table: it shows the share of source bytes already prepared (`idle` before the first broadcast, a percentage while converting, `ready` when done), with the PID/CPU/Mem of the ffmpeg doing the converting right now, and a tooltip naming the file it is on plus any file that could not be prepared. Until it reaches `ready`, a drop can find some segments missing — the player simply skips those.
6. Corrupted/"shattered"-looking picture, or a strange bitrate/codec in the player's stream stats — check OBS Settings -> Output -> **Rate Control**. If it's "Lossless", that's the cause (see [the OBS setup (Setup)](../Setup/Setup.md#4-configure-the-source-and-obs)) — switch to CBR with an explicit bitrate.
7. A brief flash of the backup video right when you click "Stop Streaming" in OBS — known, harmless timing edge. Normally the obs-source Browser Source signals the deliberate stop *before* OBS drops its RTMP connection, so the backup never shows. First thing to check: the obs-source Browser Source is actually added to a scene ([the OBS browser-source (Setup)](../Setup/Setup.md#6-add-the-browser-source)), otherwise every "Stop" looks like an ordinary disconnect (backup + timeout).
8. A source won't validate, or its platforms refuse to enable — the dashboard toasts a contract mismatch (no video track, or the wrong number of audio tracks) when what's actually arriving on that ingest path doesn't match the source's declared type/audio-track count. Fix the OBS-side output, or the source's declared track count, so they match, then reconnect.
    - With **Enable Enhanced Broadcasting** ticked, three extra checks apply and the toast names which one failed. *"video track #N is HEVC"* — a second (usually vertical) canvas is on and Twitch encodes its top rung as HEVC; turn the second canvas off. *"video tracks have different aspect ratios"* — the same cause seen from the other side (a vertical rung among horizontal ones), and it also catches a two-canvas setup on a machine with no HEVC encoder at all. *"expected N video track(s), source carries M"* — **Maximum Video tracks** in the source dialog doesn't match **Maximum Video Tracks** in OBS; set them the same, or switch the source to AUTO. Twitch caps a single canvas at 5 rungs no matter what OBS asks for.
9. An SRT platform with more than one mapped audio track disconnects a few seconds after connecting, or the platform shows an "unstable connection" warning on its own dashboard — most receivers only accept a single audio track over SRT; multitrack SRT output only holds against a platform confirmed to accept it. Map just one track and see if it holds (confirmed for Kick — see [Platform limitations](#platform-limitations) below).
10. Latency to the platform stays visibly elevated (multiple seconds, not a brief blip) after a fallback -> live cut, specifically on a source with more than one audio track (SRT, or a source feeding an RTMP+VOD platform) — this class of bug was fixed by moving that read-back onto a raw byte transport (`ffmpeg -f data`, which does not re-mux) plus the controller's own TS parser. Confirm `ffmpeg` is on `PATH` — without it the read-back can't start at all, and since a recent version the controller refuses to start rather than failing later. Doesn't apply to a plain single-track RTMP source, which never went through ffmpeg's decoding path.
11. Don't hand-edit `tmp/mediamtx.yml` — it's rendered fresh before every MediaMTX start, from a template compiled into the controller binary plus the ports and passwords in `config.json`, so a manual edit is silently overwritten on the next restart. Change `config.json` instead (ports, passwords, timeouts); the topology itself isn't meant to be tuned from outside.
12. ICMP ping (Control tab, if enabled in the System settings) shows "–" for every platform — the `ping` binary usually needs `cap_net_raw`/`net.ipv4.ping_group_range` to run unprivileged; if that's not set up on this VPS, switch the System setting back to TCP-connect ping instead (the default, and it needs no privileges). With TCP-connect ping, an SRT platform always shows "–" — SRT is UDP, there is no TCP port to probe.

13. **Windows only** — the log says `mediamtx failed to start after restart`, the Status tab shows MediaMTX `stopped`, and OBS can't connect at all. Read `logs\mediamtx.log`: `ERR ReadDirectoryChanges: Incorrect function` means the installation sits on a WSL share (`\\wsl.localhost\...` or `\\wsl$\...`). MediaMTX watches its own config file, that share doesn't implement the call, and it exits within a second of starting — nothing is listening on the RTMP port, hence OBS's "Failed to connect". There is no setting to turn the watch off; move the folder to a local disk. `install.ps1` warns about this up front.
14. **Windows only** — the controller refuses to start with `required program not found: ffmpeg` (or `ffprobe`). Both must be reachable: on `PATH`, or dropped into `bin\` next to the executable, which the controller adds to its own `PATH` at startup. `install.ps1` installs them through winget; note that a console opened *before* that install still has the old `PATH`, so open a new one.

## Platform limitations

The controller can only see its own side of the push. When an ingest accepts the connection and then drops it because of what's *inside* the stream, the Control tab cycles between Connecting/Live/Failed while the platform's own site stays offline — nothing in our logs says why. Limits we've confirmed so far:

- **Kick over SRT (AWS IVS): exactly one audio track.** The ingest drops the session a second or two after a TS with more than one mapped audio track starts flowing, over and over (Kick's dashboard may warn about an "unstable connection"). Map a single track (Track #1, the rest None) and pick *which* source track it carries instead — that switch is live, no reconnect. This is Kick's limit, not the controller's: the same OBS feed pushed straight to Kick with two audio tracks fails identically.
- **Kick over RTMPS: the panel's Server URL is incomplete.** Kick shows `rtmps://<id>.global-contribute.live-video.net/` with no port and no `/app`, while the actual ingest wants `rtmps://…:443/app/<key>`. The controller appends both automatically for `*.live-video.net` hosts — nothing to do; listed so the rewritten Final URL in the platform modal doesn't surprise you.
- **AWS IVS ingests hold a dead session open for up to about a minute.** After the push dies without a clean goodbye (VPS crash, controller killed mid-broadcast), reconnecting with the same Stream ID can keep getting rejected until the stale session times out on their side. It heals on its own — the supervisor keeps retrying.
- **VOD Track output is Twitch-only.** The second (VOD) audio track rides on an Enhanced-RTMP extension that only Twitch's ingest understands. Point an RTMP platform with **Twitch VOD Track** ticked anywhere else and the audio side will be rejected or mangled — leave the checkbox off for everything that isn't Twitch.
- **The Enhanced Broadcasting ladder is Twitch-only.** A platform whose **Video source** is *all video tracks* pushes the whole multitrack ladder, which only Twitch accepts (its Server field is ignored — the ingest URL is minted at broadcast start from the channel Stream Key). If that exchange fails, or if the ladder Twitch grants doesn't match the tracks actually arriving, the platform refuses to push and the toast says which: *"Twitch granted no renditions"* usually means Enhanced Broadcasting isn't enabled for the channel, while *"the ladder Twitch granted does not match the source"* means OBS is sending a different set of renditions than Twitch would hand out for it (check **Maximum Video Tracks** and the canvas in OBS). Its fallback video is re-encoded into every rung, so it is ready later than the other platforms' — a drop in the first moments of a broadcast can find it with nothing prepared yet, and that platform then waits for the source instead of showing the backup.
- **Twitch and "exotic" encoder profiles.** OBS Rate Control "Lossless" (NVENC High 4:4:4) produces a stream Twitch can't play properly — item 6 above; use CBR with an explicit bitrate.
